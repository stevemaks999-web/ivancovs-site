# Ivancovs — план разработки сайта и маркетинговой инфраструктуры

Статус: презентация принята, цена согласована → стартуем разработку.
Сайт клиента: WordPress (латышский интерфейс), хостинг уже есть (Nano.lv, панель cPanel; адрес и логин хранятся в менеджере паролей).

> **Доступы.** Логины/пароли НЕ храним в этом файле и в репозитории. Только в менеджере паролей. Пароли с скриншотов (хостинг, WP, Google-аккаунт) лежат на фото/в таблице открытым текстом и построены по одной схеме — после получения доступа попросить клиента сменить их, включить 2FA, а для работы завести отдельных пользователей (WP-админ для нас, делегированный доступ в Google).

## Фаза 1б. Автоматический канал деплоя (без ручной работы) — день 2
Цель: ты ничего не заливаешь руками; Claude/CI сам доставляет код на хостинг.

**Что проверено:** порт 22 (SSH) закрыт снаружи, порт 2083 (cPanel) и 21 (FTP) открыты. На shared-хостинге SSH обычно выключен по умолчанию или на другом порту — нужно включить через поддержку Nano / cPanel → «SSH Access».

**Порядок выбора канала (от лучшего):**
1. **SSH + rsync/git** — если Nano включит SSH (написать в поддержку: «включить SSH/Jailed Shell для аккаунта клиента и сообщить порт»). Я генерирую deploy-ключ, ты один раз импортируешь публичную часть в cPanel → SSH Access → Import Key → Authorize.
2. **cPanel Git Version Control + API-токен** — в cPanel создаётся репозиторий-зеркало GitHub, `.cpanel.yml` копирует файлы; GitHub Action дёргает UAPI `VersionControlDeployment/create` по токену (cPanel → Security → Manage API Tokens). SSH не нужен.
3. **FTPS/SFTP из GitHub Actions** (запасной) — отдельный FTP-аккаунт с доступом только к `wp-content/themes|plugins` проекта, деплой через `FTP-Deploy-Action`.

**Что делаем:**
- [ ] Ты один раз: войти в cPanel и создать нужное (API-токен ИЛИ импорт SSH-ключа ИЛИ FTP-аккаунт) — это 5 минут, пароли мне не передаём
- [ ] Секреты (ключ/токен) кладём в GitHub → Settings → Secrets, не в файлы
- [ ] GitHub-репозиторий `ivancovs-site`, ветки `main` (прод) и `staging`
- [ ] Workflow: push в `staging` → деплой на staging; merge в `main` → деплой на прод (с бэкапом перед выкладкой и откатом)
- [ ] WP-CLI на хостинге (если есть SSH) для обновлений/кеша; иначе — REST API + Application Password
- [ ] **Gatekeeper**: branch protection на `main`, обязательные проверки (PHP lint, сборка, тесты, проверка на секреты, Lighthouse/скорость), merge только после зелёных проверок и ревью
- [ ] Доступы для второго человека: добавить его в GitHub-репо (collaborator), отдельный пользователь WP, отдельный cPanel-аккаунт/ключ — «такие же доступы как у тебя», у каждого свои, не общий пароль

## Фаза 8. Дашборд проекта на сайте клиента — неделя 2–4 (начинаем рано, он нужен клиенту с первого дня)
Отдельная страница (напр. `/project-status`) на сайте Ivancovs, **закрытая логином клиента, noindex, не в sitemap**. Это «GitHub-дашборд» + план с галочками.

**Блоки:**
1. **План с галочками** — все фазы и задачи из этого файла; клиент видит что сделано / в работе / не начато, % выполнения по фазам. Источник правды — `PLAN.md` в репозитории (чекбоксы `- [x]`), страница его парсит и рисует.
2. **GitHub: Issues** — открытые / в работе / закрытые, метки (фаза, приоритет), исполнитель.
3. **GitHub: Pull Requests** — в разработке (draft), на ревью, смёржены; для каждого: заголовок, автор, дата, ссылка.
4. **Gatekeeper / CI-проверки** — по каждому PR статус проверок: прошёл ✅ / не прошёл ❌ / ждёт ⏳ (линт, сборка, проверка PHP, скорость, SEO-чек и т.п.) и причина отказа.
5. **Текущий этап** — наглядная шкала фаз 0–10, подсвечена текущая; последний деплой (когда, какой коммит, на staging или прод).
6. **Журнал** — лента событий: «PR #12 смёржен», «деплой на staging», «Gatekeeper отклонил PR #13: …».
7. *(позже, когда подключим)* краткие KPI: трафик GA4, клики GSC, расходы/лиды Google Ads.

**Как работает технически:**
- Репозиторий GitHub `ivancovs-site` (приватный): код темы/плагинов, `PLAN.md`, workflow-файлы.
- Данные собирает **GitHub Action по расписанию + на каждое событие** (issues, PR, check runs) → пишет `status.json` → деплоится на хостинг в папку темы/плагина.
- Страница на WP — небольшой кастомный плагин `ivancovs-status`: шорткод, рисует из `status.json` (без токенов GitHub в браузере, токен хранится только в GitHub Secrets).
- Доступ клиента: роль «Client» в WP (только просмотр этой страницы).
- [ ] Согласовать с клиентом, что именно ему показываем (скрыть внутренние комментарии/метки)
- [ ] Gatekeeper: настроить branch protection на `main` + обязательные проверки (Фаза 1б)
- [ ] Написать workflow сбора статуса, парсер PLAN.md, плагин-страницу
- [ ] Протестировать на staging, затем на проде

## Риски
- Старый сайт/плагины могут ломаться при обновлении → всегда бэкап и staging
- Без Consent Mode v2 данные и ремаркетинг в ЕС будут неполными
- Запуск рекламы до готовых страниц/конверсий = слив бюджета
- Открытые пароли в таблицах/фото → смена паролей и менеджер паролей
